# EcoGuardian

Прототип веб‑сервиса мониторинга экологической обстановки и прогнозирования экологических рисков, разработанный с использованием фреймворка Django и средств вайб‑кодинга (Cursor, большие языковые модели).

## Цель и задачи работы

**Цель работы** – разработать и проанализировать прототип информационной системы EcoGuardian для мониторинга экологической обстановки и предварительного прогнозирования экологических рисков с применением средств вайб‑кодинга и больших языковых моделей.

**Задачи работы:**

1. Проанализировать исходное описание системы EcoGuardian и определить её принадлежность к основным классам информационных систем и архитектурным подходам.
2. Спроектировать архитектуру веб‑сервиса, структуру данных и пользовательские сценарии на основе заданных требований.
3. Реализовать прототип веб‑приложения на платформе Django с использованием средств вайб‑кодинга (Cursor) и LLM в роли ассистента при проектировании и программировании.
4. Провести функциональное тестирование прототипа, выявить проблемы и ограничения текущей реализации.
5. Выполнить анализ качества кода, удобства сопровождения и потенциальной производительности прототипа.
6. Сформулировать выводы о степени успешности разработки и эффективности применения средств вайб‑кодинга.

## Краткое описание сервиса

EcoGuardian представляет собой веб‑сервис для мониторинга экологической обстановки по регионам. В системе реализованы следующие основные сущности:

- `Region` – регион мониторинга (город, парк, зона наблюдения).
- `Sensor` – тип датчика или источника данных (датчик качества воздуха, температурный датчик и т.п.).
- `Measurement` – измерение показателей (метрика, значение, отметка времени, привязка к региону и датчику).
- `Alert` – предупреждение о возможном экологическом риске для региона.

Пользовательская часть сервиса реализована в виде простого веб‑интерфейса:

- главная страница со списком регионов мониторинга;
- страница региона с описанием, списком последних предупреждений и кнопкой запуска анализа риска.

Через административную панель Django добавляются регионы, датчики и измерения, на основании которых формируются предупреждения.

## Архитектура

Сервис реализован в классической трёхзвенной архитектуре:

- **Клиентский уровень** – веб‑браузер пользователя, отправляющий HTTP‑запросы и отображающий HTML‑страницы.
- **Уровень приложения** – веб‑сервер Django (views, templates, бизнес‑логика анализа риска в модуле `services.py`, ORM‑слой).
- **Уровень данных** – база данных SQLite (`db.sqlite3`), хранящая таблицы `Region`, `Sensor`, `Measurement`, `Alert`.

Логика анализа риска инкапсулирована в функции `generate_region_risk_analysis(region)`, которая агрегирует измерения за последние 24 часа, вычисляет среднее значение и на его основе присваивает один из уровней риска (низкий, средний, высокий, критический), создавая соответствующий объект `Alert`. В реальной системе на этом месте может быть вызов внешнего LLM‑ или ML‑сервиса.

## Запуск проекта

```bash
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt

python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

После запуска сервер доступен по адресу `http://127.0.0.1:8000/`.

Административная панель – по адресу `http://127.0.0.1:8000/admin/`, через неё можно добавить регионы, датчики и измерения.

## Тестирование и анализ результата

В ходе тестирования проверялись:

- корректность отображения главной страницы со списком регионов;
- корректность перехода на страницу региона и отображения описания;
- работа кнопки «Обновить прогноз риска», создание и вывод объектов `Alert`;
- работа административной панели (создание/редактирование `Region`, `Sensor`, `Measurement`, `Alert`).

Сервис успешно выполняет базовые сценарии: после добавления измерений через админ‑панель и запуска анализа для региона формируются предупреждения с рассчитанным уровнем риска. Ошибки, обнаруженные на промежуточных этапах (отсутствие миграций, настройки шаблонов, статики), были устранены.

С точки зрения производительности прототип рассчитан на учебные объёмы данных и небольшое количество одновременных пользователей. Использование SQLite и простых операций агрегирования делает отклик системы достаточно быстрым. Для промышленного использования потребуется переход на более производительную СУБД (например, PostgreSQL), а также реализация потоковой обработки данных и интеграция с внешними источниками и моделями.

## Использование вайб‑кодинга и LLM

Средства вайб‑кодинга (Cursor, большие языковые модели) применялись:

- при проектировании архитектуры и структуры данных;
- при генерации шаблонного кода моделей, представлений, маршрутов и шаблонов;
- при формулировании текста отчёта, целей, задач и анализа.

Это позволило сократить время на рутинные операции и сосредоточиться на логике предметной области. Вместе с тем потребовалась ручная проверка и доработка сгенерированного кода (исправление настроек, упрощение шаблонов, правка миграций), что подчёркивает необходимость критического отношения к автоматически полученным решениям.

## Рефлексивное заключение

В результате работы удалось реализовать минимально жизнеспособный прототип веб‑сервиса EcoGuardian, отражающий основные требования к системе мониторинга экологической обстановки и формирования предупреждений о рисках. Ключевой функционал (работа с регионами, датчиками, измерениями, генерация предупреждений) был успешно протестирован.

Основные сложности были связаны с настройкой структуры Django‑проекта, миграций и административной панели, а также с интеграцией и корректировкой кода, сгенерированного при помощи больших языковых моделей. Использование вайб‑кодинга показало свою эффективность при решении типовых задач (создание моделей, представлений, шаблонов), но потребовало внимательного контроля и понимания внутренних механизмов фреймворка.

Полученный опыт позволил углубить знания о разработке веб‑приложений на Django, освоить базовые приёмы проектирования архитектуры и структуры данных, а также на практике оценить преимущества и ограничения использования LLM как инструмента поддержки программирования.
